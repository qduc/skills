# Real-use verification

When delivering a new or materially changed skill or orchestration capability,
require a fresh agent using the shipped skill on a representative real repository
task before declaring it done. This is the default completion gate. The user may
explicitly waive it; preserve that decision and its limits with the result.

## Choose and run the task

Use a genuine authorized repository need with an observable useful deliverable:
a feature, repair, or workflow change with real consumers. Work in a reversible
local checkout when appropriate. A toy loader invented for the evaluation, a
tabletop response, or a script that drives helper APIs bypasses the full-skill gate.
Match the task to the changed capability; an unrelated trivial edit cannot validate
coordination, dependency handling, or integration behavior.

Give a fresh agent the actual user request, repository location, shipped skill
path, authority, and minimum raw context. Have it read the skill and choose its
workflow. Leave decomposition, commands, delegation, evidence gathering, and
recovery to the skill-guided agent. Supplying the author's intended implementation
or an exact helper-command sequence would hide instruction failures. Record any
author intervention and the resulting limits on the evidence.

Use the available host/runtime within the confirmed pool. The agent owns this
bounded repository task; the parent owns the validation decision. Evaluate the
behavior that changed. For Coordinator, observe actual task understanding,
ownership/dependencies, bounded worker delivery when warranted, durable state,
independent verification, integration, and final goal acceptance. Do not manufacture
unnecessary workers or failures to inflate coverage. Exercise additional changed
runtime paths when they need their own real-use evidence.

## Accept the evidence

Before the run, state the user-visible acceptance criteria. After it, inspect the
actual deliverable and independently run the relevant repository checks against
the resulting artifact. Check the intended user workflow and authority as well as
component tests. A worker's report does not establish acceptance.

Retain the real task and deliverable, exact skill version or content hashes, agent
identity, execution trace and durable task records, actual commands/results,
expected versus observed behavior, author interventions, and acceptance decision.
Separate unsuccessful/interrupted attempts from successful ones. Account for owned
workers and processes before closing.

A pass requires the real task's acceptance criteria, the exercised skill behavior,
and independent inspection to agree. Fix an observed defect and rerun the affected
real workflow before accepting it. Passing fixtures and tabletop cases remain
supporting evidence with their own labels.

If access, tools, or authority prevent this gate, retain it as pending and identify
the missing prerequisite. Existing test results remain valid, but overall real-use
verification and completion stay unclaimed. A wording-only change does not require
an evaluation of this evaluation procedure; verify that edit directly.
